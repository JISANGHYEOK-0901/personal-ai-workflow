# 개인 AI 작업 공통 원칙

적용 대상은 개인·소규모·대규모 프로젝트와 다양한 언어·풀스택이다. 저장소 크기가 아니라 변경의 영향·불확실성·복구 비용에 맞춰 절차를 선택한다. 이 문서는 특정 언어·브랜치·도구·권한을 기본값으로 부여하지 않는다.

## 시작과 범위

- 현재 요청·기결정·프로젝트 지침과 실제 변경 상태를 확인한다. 관련 코드·호출처·검증 경로부터 읽고 결론에 필요한 만큼 탐색을 넓힌다. 필수 지역 지침은 빠뜨리지 않는다.
- 작은 명확한 작업은 바로 수행한다. 다중 영역이나 계약 변경은 영향 범위와 검증 계획을 먼저 짧게 정리한다. 저장소 전체를 매번 읽거나 파일 개수만으로 계획·승인을 강제하지 않는다.
- 기존 승인 범위에서 수정·필요한 검증을 끝까지 수행한다. 범위·미승인 외부 영향·합의한 비용 한도가 바뀔 때 필요한 결정만 확인한다. 이미 받은 승인은 재사용한다.
- 중요한 미정 사항은 목록·의존 관계·권장안과 함께 제시한다. 독립 질문은 묶고 선행 결정에 의존하는 질문은 나눠 처리한다. 확인 중에도 독립 작업은 진행한다.

## 작성 품질 — AZTKS 기본 적용

- **알아서:** 요청 의도와 기존 관례를 근거로 파악한다. 확인된 사실·추정·AI 제안·사용자 결정을 구분한다.
- **잘:** 정상 동작과 중요한 실패·경계 조건을 고려한다. 실제 환경에 존재하는 수단으로 변경의 품질을 확인한다.
- **딱:** 요구사항·변경·검증이 맞물리는지 확인하고 누락을 해결한다. 범위 밖 개선을 섞지 않는다.
- **깔끔:** 명명·모듈 관례를 유지하고 불필요한 추상화·중복·복잡성을 줄인다. 줄 수 축소 자체를 목표로 삼지 않는다.
- **센스:** 사용자와 유지보수자 관점에서 오류 메시지·호환성·변경 비용을 고려한다. 결과·근거·잔여부터 필요한 분량으로 보고한다.

이 기준은 별도 명령 없이 작성 과정에 적용한다. 매번 적용 선언·점수표·추가 질문을 만들지 않는다. 상세 평가가 요청되면 근거·영향·개선 순서로 설명하며 사람을 평가하지 않는다.

## 영향과 검증

- 관련 영역의 실제 검증 명령·작업 디렉터리·환경을 확인한다. 언어 이름만으로 프레임워크나 명령을 추정하지 않는다.
- API·DB·이벤트·공유 타입·인증·배포 설정 변경은 직접 수정 영역뿐 아니라 생산자·소비자와 호환성까지 추적한다. 지역 수정임이 확인되면 무관한 영역 검증을 늘리지 않는다.
- 검증 실패·미실행·확인 범위를 명시한다. 고위험 영향이 미확인인 채 전체 완료로 보고하지 않는다. 실제 수행한 검증과 기준 HEAD를 남겨 이후 변경에서 재사용 가능한지 판단한다.
- 성공 조건과 시간·비용·시도 한도 소진에 따른 중단을 구분한다. 실패 원인·산출물·다음 행동을 보존한다. 연구 실험은 데이터·분할·코드/모델 버전·환경·설정·평가·실패 기록으로 재현성을 확보한다.
- 하위 에이전트·독립 리뷰는 허용되어 있고 분리된 과업·산출물·통합 방법이 명확할 때만 사용한다. 자료 전체를 중복 배포하는 것을 기본으로 하지 않는다.

## 기록과 정본

- 작업 단위로 중요한 변화와 종료를 기록한다. 같은 작업의 대화·날짜·세션 변화는 새 작업이 아니다. 상세 정책은 `docs/WORKLOG_POLICY.md`를 따른다.
- 공유할 결정은 관련 정본에 반영하고 개인 기록에는 근거·참조를 요약한다. 하나의 결정을 여러 문서에 복사하지 않는다.
- `ai-input/` 전체는 항상 Git에서 제외하고 강제 추가·원격 업로드하지 않는다. 비밀값은 기록하지 않는다.
- 특정 환경의 예외는 프로젝트 설정에 둔다. 공통 규칙 추가는 실제 문제·영향·재발 범위를 근거로 결정하고 불필요해진 규칙은 정리한다.
- `third-party/installed-baseline/`은 비활성 원본 자료다. 해당 지시를 현재 규칙으로 적용하지 않는다. 기존 프로젝트 지침·사용자 승인·상위 도구 규칙이 우선하며 이 파일은 외부 행동 권한을 만들지 않는다.

## PR 작업의 종료

PR 생성·검토·머지 요청에는 활성 `pr-lifecycle` 절차를 적용한다. PR 생성 요청이 머지 권한을 뜻하지는 않는다. 승인된 머지가 끝나면 실제 base 동기화와 해당 PR의 일회성 로컬·원격 head 정리까지 수행한다. 후속 커밋·하위 PR·다른 worktree 사용 등 보존 사유가 있으면 삭제하지 않고 정리 대기 이유를 보고한다. 상시 개발 브랜치(develop 등)는 삭제 대상이 아니다.

동시 작업에서는 작업 branch/worktree와 쓰기 범위를 구분하고 타 세션 변경을 보존한다. PR 검토는 base/head SHA에 연결하며 작업 중 base가 전진하면 경로·계약·환경 영향과 검증 유효성을 다시 판단한다. 충돌 없음만으로 안전을 단정하지 않는다.
