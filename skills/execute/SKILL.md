# 목표에서 검증된 결과까지

이미 허용된 작업을 실제 산출물과 확인 가능한 결과까지 이어간다. 규모·언어별 고정 절차 대신 변경 영향에 맞춘다. 프로젝트 공통 지침이 제공하는 품질·권한·기록 기준을 따르며 스킬이 추가 권한을 부여하지 않는다.

## 시작

현재 요청, 기결정, 관련 작업 기록과 지역 지침을 읽는다. 프로젝트에 `PROJECT.md`가 있으면 관련 설정을 사용하고, 없으면 현재 저장소의 문서·manifest·CI·검증 자산에서 필요한 값을 확인한다. 설정 파일 생성을 작업의 선행 의무로 만들지 않는다.

목표·범위·완료 증거와 기존 동작·데이터에 미치는 중요한 영향·미결사항을 초기 조사에서 확인한다. 문서·설정·도구 조회로 확인할 사실은 직접 조사한다. 중요한 영향·미결사항은 이에 의존하는 구현·외부 실행 전에 권장안·다음 행동과 함께 짧게 설명한다. 이미 확인된 사실도 사용자 선택을 바꾸면 전달 대상이다. 여러 항목은 `항목 | 확인된 사실/미확인 | 선행 조건·영향 | 권장안 | 다음 조사 또는 사용자 결정` 형태의 짧은 목록이나 표로 보여줄 수 있다. 내부 계획·작업 기록으로 사용자 전달을 대신하지 않는다.

예를 들어 여러 앱의 PR·자동 검사·외부 게시가 함께 요청되면 앱별 실제 PR 대상, 검사 실행 가능 여부와 실패 시 머지 차단 여부, 게시 연결·쓰기 권한·완료 확인 수단을 초기에 조사한다. 검사 실행 성공과 서버의 머지 차단 설정은 구분한다. 이 예시를 무관한 작업의 필수 체크리스트로 적용하지 않는다.

조사가 막힌 항목은 미확인과 다음 확인 방법을 목록에 남기고, 결과·범위·권한·비용에 실제 선택이 필요한 항목만 질문한다. 환경·설정 조사로 정할 실행 방법까지 사용자 결정으로 넘기지 않는다. 명시된 "준비만"·"읽기 전용" 등의 범위는 확정값이며 후속 실행 범위를 미리 재승인받지 않는다. 페이지·브랜치 이름만으로 공개 여부나 권한을 단정하지 않는다.

독립 질문은 묶고 이미 받은 결정·승인은 재사용한다. 앞서 알린 미결사항은 후속 조사·결정에 따라 확정, 승인 범위 안에서 적용할 권장 기본값, 잔여로 연결한다. 사용자 결정이 필요한 항목은 권장안만으로 확정하지 않는다. 한 단계의 미확인을 전체 작업의 차단 사유로 확대하지 않고, 결정에 의존하지 않는 조사·초안은 계속한다. 새로 발견한 중요한 영향·미결사항은 다음 의존 실행 전에 알리며 이미 설명·결정한 내용은 반복하지 않는다. 실제 사용자 결정이 필요하지 않으면 바로 진행하고 형식적인 목록·질문을 만들지 않는다. 복잡한 작업에는 짧은 영향·검증 계획을, 반복 실험에는 합의한 한도를 둔다. 작은 수정에 별도 계획 문서를 강제하지 않는다.

새 결정이나 진행 장애가 생기면 확인 가능한 사실, 승인 범위의 가역적 MINOR 결정, 사용자 검토가 필요한 MAJOR 결정, 실제 BLOCKER를 구분한다. 시간·비용·시도 한도는 재시도와 종료를 통제할 뿐 새로운 권한을 만들거나 MAJOR를 MINOR로 낮추지 않는다. 분류 기준과 변경 작업의 최종 검토는 [결정 분류와 diff 검토](references/decision-diff-review.md)를 따른다.

## 탐색과 실행

관련 진입점 → 구현 → 호출처/소비자 → 검증 경로를 확인한다. 일치 검색만으로 영향 부재를 단정하지 않는다. 파일 크기나 전체 코드 줄 수로 작업의 위험을 판단하지 않는다.

다중 서비스·언어, 공유 계약·데이터·인증·이벤트 또는 동적 호출이 관련되면 [영역 간 영향 추적](references/cross-component.md)을 읽는다. 국소 변경에 이 절차 전체를 적용하지 않는다.

기존 관례에 맞춰 수정하고 요구·변경·검증을 대조한다. 범위 밖 개선은 분리한다. 작업 중 새 사용자 메시지는 기존 목표의 보완인지 확인하고 반영한다. 실패 시 원인을 좁혀 필요한 확인만 반복하고 무관한 전체 검증을 재실행하지 않는다.

## 검증과 종료

검증 명령은 실제 manifest·CI·문서에서 확인한다. 작업 디렉터리·도구 버전·환경·외부 부작용을 확인한 뒤 필요한 검증을 수행한다. 문서라면 근거·링크·정합성을, 실험이라면 분할·환경·설정·평가·실패 기록을 확인한다.

파일을 변경한 작업은 종료 전에 기준 상태와 현재 상태 사이의 최종 diff를 직접 검토한다. 테스트·린트·`git diff --check` 성공은 의미적 diff 검토를 대신하지 않는다. 요구·기결정에 대응하지 않는 변경, 누락된 소비자, 예상 밖 삭제·설정·계약·데이터·권한 영향을 확인하고, 수정 뒤 바뀐 최종 diff와 필요한 검증을 다시 확인한다. 상세 기준과 남길 증거는 [결정 분류와 diff 검토](references/decision-diff-review.md)를 적용한다.

여러 검증·조회 명령을 묶을 때는 중간 검증 실패가 뒤의 성공한 명령에 가려지지 않도록 실패 전파나 단계별 종료 상태를 보존한다. 묶음의 최종 종료 코드만으로 전체 통과를 판단하지 않는다.

UI 배치를 변경하면 대상 화면 크기의 실제 렌더링에서 핵심 정보와 주요 조작의 접근성을 확인한다. 모바일을 지원한다면 좁은 화면에서 관련된 긴 텍스트·번역·빈 상태 등 대표 조건을 사용해, 중요한 정보가 긴 제목이나 과도한 여백에 밀리고 페이지·대화상자 사이에 불필요한 반복 스크롤이 생기는지 살핀다. 필요한 세로 스크롤은 허용하며, 한 화면에 맞추려고 필수 정보를 숨기거나 글자·조작 영역을 과도하게 줄이지 않는다. 변경 영향에 맞는 대표 화면과 조작 결과를 근거로 남기고, 실제 화면 확인이 불가능하면 그 한계를 명시한다.

완료는 목표 충족과 필요한 증거가 있을 때다. 부분 검증을 전체 성공으로 보고하지 않는다. 한도에 도달하면 중단 상태와 재개 조건을 남긴다. 보고는 결과·검증 범위·잔여 위주로 하며 자기점수표를 강제하지 않는다.

작업 종료나 중요한 변경에서 프로젝트의 기존 worklog를 갱신한다. 같은 작업을 새 대화 항목으로 복제하지 않는다. 검토만 요청된 경우 결과 검토가 목표이며 무단 수정·배포로 전환하지 않는다.
