# 규칙 채택 후보와 검증 사례

상태: 사용자 승인 후 단계적으로 적용하는 채택 목록. 공통 원칙·execute·프로젝트 설정을 v0.1로 구현했다. 확장 항목과 행동 검증은 구현·검증 기록에서 구분한다. 사용자 확정 사항은 작업 단위 기록·월별 폴더·ai-input 전체 제외이며, AZTKS 내재화는 사용자가 제시한 설계 방향이다. 나머지는 검토할 권장안이다.

[전체 설계](PERSONAL_WORKFLOW_DRAFT.md)와 함께 읽는다. 아래 30개는 검토용 세부 항목이며 공통 프롬프트에 30개를 그대로 넣지 않는다. 구현할 때 중복을 합쳐 짧은 공통 원칙과 선택 절차로 배치한다.

## 적용 구분

- 공통: 작업 종류와 무관하게 유지할 기준. 상황별로 필요한 행동만 수행한다.
- 선택: 해당 과업이 있을 때 적용하는 절차. 슬래시 호출을 의무화하지 않는다.
- 설정: 프로젝트·도구·권한에 따라 채울 값과 조건.
- 확장: 실제 필요가 생길 때 구현할 전문 기능.

## 초기 도입 순서

1. R01~R14를 중복 제거해 공통 작성·검증·보고 원칙으로 통합한다. R27·R30은 탐색 범위와 규칙 변경 기준에 함께 녹인다. 작업 기록은 기존 WORKLOG_POLICY.md를 재사용한다.
2. execute 하나에서 R18의 목표·검증·한도를 적용하고 V01·V05·V06·V07·V08·V09로 기본 흐름을 검증한다. 모든 사례를 매 작업마다 돌리지 않는다.
3. 실제 기획·리뷰 요구가 쌓이면 R15~R17·R19를 별도 스킬로 분리한다. 프로젝트 이동 시 R20·R23을 구체화한다.
4. PR·상황판·백업·프로필은 사용 필요에 따라 확장한다. 연구 프로젝트 착수 시 R29를 적용한다. 하위 에이전트 R28은 기본 실행 조건이 아니다.

## 측정과 규칙 수정

- 기록: 과제·지침 버전·도구/모델·입력·승인 범위·시간·토큰(입력/캐시/출력 구분)·결과·재작업.
- 불필요한 질문: 이미 답이 있거나 승인된 범위의 행동을 다시 승인받으려는 질문. 새로운 중요 결정을 묻는 질문은 비용이 있어도 불필요로 세지 않는다.
- 판단 순서: 사실·동작·범위 준수 → 검증·재현성 → 질문·재작업 → 시간·토큰. 비용 개선만으로 품질 저하를 정당화하지 않는다.
- 일회 실행 결과로 일반화하지 않는다. 성능 비교를 주장하려면 동일 조건의 반복 실행과 변동을 확인하고 사전 평가 기준을 둔다.
- 초기 통과 기준은 행동·산출물의 존재와 위반 여부다. 시간·토큰 절감률 목표는 기준 측정 전 임의로 확정하지 않는다.

## 규모·언어 독립 적용 조건 (사용자 보완)

개인·소규모·30만 줄 이상 대규모 프로젝트 모두가 대상이다. PHP·Next.js·Spring은 예시이며 지원 범위를 세 기술로 제한하지 않는다. 큰 저장소의 작은 수정에는 지역 검증을, 작은 저장소의 경계 변경에는 계약·통합 검증을 적용한다. execute의 cross-component 참조와 프로젝트 설정 템플릿으로 구현했다.

추가 행동 검증 과제: 작은 단일 언어 수정 / 작은 풀스택 계약 변경 / 큰 저장소의 국소 수정 / 다중 언어 서비스 계약 변경을 각각 실행해 탐색 누락과 불필요한 전수 작업을 평가한다. 이번 파일·동기화 검사는 이 실제 행동 검증을 대체하지 않는다.
