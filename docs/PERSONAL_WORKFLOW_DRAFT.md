# 개인 AI 작업 체계 설계 초안 v0.1

상태: 채택 방향에 기반한 설계 기록. v0.1 구현의 실행 정본은 ../workflow/CORE.md와 ../skills/execute/SKILL.md다. 이 문서의 후속 확장 제안은 구현 완료를 의미하지 않는다.

## 1. 목표와 확정 범위

ly의 범위·권한·검증·기록에 관한 일관성과 설치한 스킬의 다양한 업무에 적용 가능한 방법론을 결합한다. 개인이 여러 프로젝트에서 재사용하고 실제 사용 기록으로 개선할 템플릿·스킬셋을 만든다.

**사용자가 확정한 사항**

- ly와 설치한 8개 스킬 양쪽에서 장점을 추출한다.
- 개인·소규모·대규모 프로젝트 모두에 적용하며 PHP·Next.js·Spring 등 기술 차이는 프로젝트 설정과 실제 근거로 처리한다.
- AI 대학원 준비용 개인 프로젝트를 수행할 의도가 있으며, 실무 전반에도 적용할 수 있어야 한다.
- worklog는 매 대화가 아닌 작업 단위로 관리한다. 월별 폴더를 사용한다.
- `ai-input/` 전체는 항상 Git에서 제외한다.

**아래 설계는 권장안**이다. 스킬 이름·개수·절차 강도·연구 주제는 확정하지 않았다. 첫 버전의 범위는 공통 원칙과 선택형 작업 절차의 설계다. 범용 자동화 엔진, 상황판 전체, 새 하위 에이전트 조직은 첫 버전에 포함하지 않는다.

## 2. 설계의 중심: 원칙은 공통, 절차는 작업에 맞게

| 계층 | 책임 | 담지 않을 것 |
|---|---|---|
| 공통 원칙 | 근거·권한·범위·완료 판단·기록의 최소 기준 | 특정 프레임워크 명령과 일률적인 승인 단계 |
| 선택형 스킬 | 결정 정리, 목표·실행, 결과 검토의 구체 절차 | 동일한 공통 규칙의 복제 |
| 프로젝트 설정 | 실제 검증 수단, 문서 경로, Git 방식, 자원 한도 | 사용자 승인과 무관한 새 권한 부여 |
| 도구별 연결 | 공통 원본을 각 도구가 읽도록 연결 | 지원하지 않는 기능을 지원한다고 가정 |

공통 원칙은 짧은 정본 한 곳에 둔다. 도구별로 원본을 복제해 수정하기보다 연결 파일을 관리한다. 스킬 헤더·hook 등 도구에 종속된 부분은 실제 지원 여부를 확인한 뒤 구현한다. 현재 scripts/sync_skills.py가 스킬 사본을 동기화한다. 공통 원칙은 연결 문서에서 읽는다.

## 3. 공통 원칙 후보

1. **의도와 사실:** 현재 요청·기결정·관련 근거를 먼저 확인한다. 확정 사실, 사용자 선택, AI 추정을 구분한다.
2. **탐색 범위:** 작업에 필요한 진입 문서와 근거부터 읽는다. 규칙상 필수인 문서는 따르되, 관련 없는 자료의 전체 탐색은 기본 절차로 만들지 않는다.
3. **자율 진행:** 이미 허용된 범위의 구현·수정·필요한 검증을 계속한다. 같은 권한을 반복 확인하지 않는다.
4. **새 결정:** 목표·범위·외부 영향·합의한 자원 한도가 달라질 때 그 결정에 필요한 선택과 근거를 제시한다. 확인 대기 중에는 독립적으로 진행 가능한 일을 수행한다.
5. **검증:** 실제 존재하는 검증 수단을 사용한다. 구현·실험·문서의 완료 증거는 각각 다르게 정의한다.
6. **종료:** 성공 조건 충족과 한도 도달에 따른 중단을 구분한다. 테스트 통과가 연구 가설의 참을 뜻하지는 않는다.
7. **기록:** 작업의 중요한 변화와 종료를 기존 작업 ID에 갱신한다. 원문 대화와 중복 문서를 계속 늘리지 않는다.
8. **보고:** 결과·필요한 근거·남은 일부터 전달한다. 고정 평가표나 형식은 독자에게 도움이 될 때만 사용한다.

적용 환경의 상위 지침과 기존 사용자 승인을 존중한다. 프로젝트 설정이나 스킬 선택이 새로운 배포·공유·삭제 권한을 만들지는 않는다.

### AZTKS를 기본 작성 기준으로 내재화

별도 명령을 기억해야 품질 기준이 적용되는 구조를 피한다. AZTKS의 APPLY 기준을 공통 원칙과 실행 과정에 녹이고, 상세 EVALUATE는 자연어 평가 요청 등으로 선택할 수 있게 한다. 설치 원본도 description에서 자동 적용을 의도하고 있으므로 슬래시 전용이라고 전제하지 않는다. 실제 도구의 선택 여부에 기대기보다 개인 공통 정본에 기준을 명시하는 것이 이 설계의 목적이다.

| 기준 | 코드 작성 과정에서의 구체 행동 |
|---|---|
| A 알아서 | 관련 코드·호출처·기존 관례·기결정을 먼저 읽고 요청 의도를 확인한다. 무관한 전체 탐색은 하지 않는다. |
| Z 잘 | 정상 동작과 중요한 실패·경계 조건을 확인하고, 변경에 맞는 검증으로 근거를 남긴다. |
| T 딱 | 요구사항·변경·검증이 서로 맞는지 확인한다. 승인 범위의 누락을 해결하고 범위 밖 개선을 섞지 않는다. |
| K 깔끔 | 기존 구조와 명명 관례를 따르고, 중복·불필요한 추상화·읽기 어려운 제어 흐름을 줄인다. |
| S 센스 | 유지보수자와 사용자의 관점에서 오류 메시지·호환성·변경 비용을 고려하고 중요한 결과부터 설명한다. |

실행 흐름은 관련 근거 확인 → 기존 구조에 맞는 구현 → 요구·변경 대조 → 필요한 검증 → 결과·잔여 보고다. 매번 AZTKS 적용 선언·점수표·별도 기록·추가 승인 단계를 만들지 않는다. 평가표는 요청되거나 상세 비교에 도움이 될 때만 사용한다. 이 기준은 범위 확대나 반복 리팩터링의 근거가 아니며, 완료 조건과 자원 한도 안에서 적용한다. 문서·실험 업무도 같은 기준을 쓰되 코드 전용 행동은 해당 산출물에 맞게 바꾼다.

## 4. 절차 강도 선택

| 상황 | 권장 절차 | 사용자 확인 |
|---|---|---|
| 목표가 명확한 작은 수정·조회 | 바로 수행 → 필요한 확인 → 결과 | 새로운 결정이 생기지 않으면 추가 확인 없음 |
| 여러 구성요소 변경·조사·비교 실험 | 짧은 범위·검증 계획 → 수행 → 증거 정리 | 기존 승인 범위 활용, 중요한 미정 사항만 질문 |
| 외부 공유·운영 변경·큰 비용 등 영향이 큰 작업 | 영향·복구·검증 방법 명시 → 실행 준비 → 확인된 권한으로 실행 | 미승인 행동과 한도 변경만 확인 |

파일 개수만으로 강도를 정하지 않는다. 한 줄 변경도 운영 데이터에 영향을 주면 별도 판단한다. 간단한 작업을 이유 없이 계획 인터뷰나 독립 에이전트 검토로 확대하지 않는다.

## 5. 선택형 스킬 계약 후보

| 가칭 | 사용 시점 | 입력 | 산출물·종료 |
|---|---|---|---|
| clarify | 중요한 목표·범위·선택이 미정 | 참조 범위, 목적, 기결정 | 미결정 목록과 권장안, 결정·근거 기록. 다음 작업에 필요한 결정이 해소되거나 사용자 한도에 도달하면 종료 |
| execute | 실행할 목표가 정의됨 | 목표, 범위, 검증 수단, 자원 한도 | 산출물과 검증 증거. 성공/중단/실패를 구분하고 잔여 기록 |
| review | 평가할 결과물이 존재함 | 산출물, 목표, 증거 | 근거가 있는 문제와 개선 우선순위. 수정은 이미 허용된 범위에서만 수행 |

세 스킬을 항상 순서대로 호출하지 않는다. 명확한 작업은 execute로 바로 시작하고, 결과 확인만 필요하면 review만 쓴다. clarify에서 해소된 결정은 execute가 다시 묻지 않는다. 실행 중 중요한 미정 사항이 생기면 해당 토픽만 clarify 절차로 처리한다.

단순 자기점검은 실행 과정에 포함한다. 독립 리뷰·하위 에이전트는 별도 필요와 권한이 확인된 경우만 사용한다. 현재 execute를 구현했으며 clarify·review 별도 스킬 분리는 후속 필요에 따른다.

## 7. 프로젝트 설정 템플릿 예시

설정은 사람이 읽는 Markdown으로 시작한다. 실제 파서가 없는 YAML과 자동 라우터를 먼저 만들지 않는다.

```markdown
# 프로젝트 설정
- 목적·산출물:
- 작업 범위와 제외 범위:
- 근거 문서 위치:
- 검증 수단: 실제 명령 또는 문서·실험 평가 기준
- Git: 사용 여부, 기본 브랜치, 머지 방식
- 외부 행동: 기존 승인 범위와 새 확인이 필요한 행동
- 자원 한도: 시간·비용·시도 횟수 중 실제 합의값
- 완료 조건과 중단 시 보존할 결과:
- 작업 기록: ai-input/worklog/YYYY-MM/YYYY-MM-DD.md
```

기존 프로젝트에서 확인 가능한 값은 먼저 읽어 채운다. 빈 항목을 모두 질문하지 말고 현재 작업을 막는 항목만 확인한다. 검증 명령이 없으면 존재하지 않는 명령을 만들지 않고 문서 검사·수동 재현 등 현실적인 기준을 제안한다.

## 8. 실제 적용으로 검증할 것

| 사례 | 관찰할 증거 | 실패 신호 |
|---|---|---|
| 작은 버그 수정 | 재현 결과와 수정 후 확인, 질문 횟수 | 명확한 요청인데 승인 반복, 무관한 파일 탐색 |
| AI 비교 실험 | 데이터 분할·모델/설정·seed·평가 결과·실행 환경 | 유리한 결과만 보고, 데이터 누수, 한도 도달을 성공으로 기록 |
| 조사·기획 문서 | 근거와 추정 구분, 사용자 결정, 미해소 항목 | AI 제안을 사용자 확정으로 승격, 질문·문서 중복 |
| 다음 세션 재개 | 동일 작업 ID, 기존 결정 재사용 | 기존 작업을 복제하거나 결정·시각을 이유 없이 변경 |

처음에는 사례별 실제 기록으로 개선점을 찾는다. 효과 비교 시 같은 과제·도구·모델·입력을 가능한 한 맞추고 지침 버전을 남긴다. 성공률·재작업·불필요한 질문·시간·토큰을 관찰하되 미측정은 미측정으로 적는다. 소수 사례를 연구적 우위의 증명으로 해석하지 않는다. 구체 예산·평가 과제는 적용 전에 정한다.

## 9. 다음 구현 단위와 검토 포인트

권장 첫 구현 단위는 **공통 원칙 정본 + 프로젝트 설정 예시 + execute 스킬 하나**다. 현재 초안의 세 계약을 모두 구현하기보다 명확한 작업 하나를 끝까지 수행하는 흐름부터 확인한다. clarify와 review는 반복되는 필요가 확인되면 분리한다.

검토할 핵심은 다음 세 가지다.

1. 작업 영향에 따라 절차 강도를 바꾸는 기준이 본인의 통제 방식에 맞는가?
2. execute 하나부터 구현하는 범위가 충분한가?
3. 첫 적용 사례를 어떤 실제 작업으로 잡을 것인가?

초안 작성 완료 기준: 사용자 확정/제안 구분, 양쪽 출처와 변형 이유, 작업·프로젝트 경계, 검증 시나리오, 미정 사항이 문서에 존재한다. 실제 스킬 구현·실험·성능 검증은 별도 완료 조건이다.
