# 영역 간 영향 추적

사용 조건: 다중 언어·서비스, 공유 라이브러리·API·DB·이벤트·인증·배포 계약 또는 동적 호출이 관련된 변경. 소규모 풀스택 앱에도 적용할 수 있고, 대규모 저장소의 독립 문서 수정에는 전체 적용할 필요가 없다.

## 지도를 필요한 만큼 확보

기존 아키텍처·workspace·manifest·CI·지역 지침에서 관련 서비스 경계와 검증 진입점을 찾는다. PHP는 composer.json·라우트/컨테이너 설정, Next.js는 package.json·라우트/서버 경계, Spring은 Maven/Gradle·컨트롤러/설정 등이 탐색 단서다. 해당 언어라는 이유만으로 특정 프레임워크나 테스트 명령을 가정하지 않는다.

전체 파일 목록을 모두 읽는 대신 관련 경계와 책임을 요약한다. 기존 프로젝트 지도는 출처·기준 커밋과 실제 파일을 대조하고 이동·새 서비스·계약 변경이 있으면 관련 부분만 갱신한다. 지도 부재가 당장 필요한 국소 수정의 자동 차단 조건은 아니다.

## 생산자와 소비자

변경별로 필요한 항목을 확인한다.

| 경계 | 확인할 영향 |
|---|---|
| UI ↔ API | 요청·응답·nullable·상태 코드·오류 형태·클라이언트 소비 |
| 서비스 ↔ DB | schema·조회·migration 순서·기존 데이터·rollback 가능성 |
| 서비스 ↔ 이벤트/배치 | producer·consumer·payload 버전·재시도·멱등성 |
| 공유 코드·타입·생성물 | 소비 서비스·생성 원본·생성 명령·재생성 필요성 |
| 인증·권한·환경 | 프런트 표시와 서버 강제의 차이·설정 경로·배포 순서 |

검색에 호출처가 없더라도 라우팅·DI·reflection·코드 생성·이벤트 구독 같은 간접 연결을 고려한다. 관련 설정과 기존 통합/계약 테스트로 확인한다. 외부 소비자를 확인하지 못하면 불확실성을 표시하고 호환성 변경의 완료를 단정하지 않는다.

여러 저장소에 걸친 영향은 기록하되 다른 저장소 수정 권한을 추론하지 않는다. 허용된 범위에서 호환 경로를 유지하거나 필요한 결정을 확인한다.

## 검증 선택

수정 영역의 집중 검증 → 확인된 소비자의 계약/통합 검증 → 사용자 흐름 검증 중 필요한 것을 고른다. 필수 프로젝트 게이트는 생략하지 않는다. 영향 범위가 넓거나 불명확하면 검증을 확대한다. 모든 서비스 빌드가 항상 필요한 것도, 변경 파일의 단위 테스트만 충분한 것도 아니다.

범위가 큰 경우 작업 메모에 다음을 남긴다: 기준 HEAD, 변경 경계, 생산자·소비자, 확인한 지침, 수행한 검증과 결과, 미확인 영향, 호환성·배포 순서. 작은 작업은 답변·기존 worklog에 필요한 만큼만 남긴다.
