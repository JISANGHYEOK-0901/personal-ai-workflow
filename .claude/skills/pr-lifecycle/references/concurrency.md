# 동시 작업과 base 전진

모든 PR에서 snapshot과 최종 신선도를 확인한다. 아래 상세 분기는 base/head 이동, 여러 세션·worktree, 공유 브랜치, PR 스택, 머지 큐가 있을 때 적용한다. base는 PR의 실제 대상이며 develop/main 이름에 의존하지 않는다.

## 1. 검토 기준을 이름 대신 SHA로 남긴다

최소 기록: 저장소·remote·PR 번호, base 이름과 SHA(B0), head 이름과 SHA(H0), merge-base, 작업 branch/worktree, 검증 대상(단독 head 또는 B0와 H0의 통합 결과), 검증 명령·결과, 검토 결론·미해결 사항. 기존 작업 기록/PR 본문에 필요한 만큼 남기며 별도 시스템 구축을 강제하지 않는다.

초기 fetch, 검증 직전, push 직전, 머지 직전에 원격 상태를 확인한다. 장시간 작업은 의미 있는 checkpoint에서 확인한다. 매 도구 호출마다 fetch하지 않는다. 원격 조회 실패를 이전 상태가 유효하다는 근거로 쓰지 않는다.

현재 base/head가 B0/H0와 다르면 기존 검토·검증의 유효성을 다시 판단한다. head 전진과 base 전진은 따로 기록한다. diff가 같은 것처럼 보여도 CI 설정·의존성·스키마·외부 계약 변화가 검증 환경을 바꿀 수 있다.

## 2. 동시 작업의 쓰기 경계

- task별 작업 branch와 worktree를 분리하는 것을 권장한다. 동일 branch/worktree를 다른 세션이 사용 중이면 커밋·전환·rebase·reset·정리를 하지 않는다. 소유권과 작업 배분을 먼저 확인하거나 별도 worktree에서 독립 작업한다.
- 새 worktree는 현재 프로젝트의 배치 관례와 승인된 경로 안에 만든다. 작업 분리가 다른 저장소 쓰기 권한을 만들지는 않는다.
- 실행 전 현재 branch/HEAD와 작업 소유 파일을 확인한다. 모르는 변경·index 내용은 보존한다. 동일 파일의 소유가 섞였으면 일괄 stage·stash·clean하지 않는다.
- worktree가 분리돼도 refs·remote-tracking·일부 Git 설정은 공유된다. 다른 세션이 fetch해 바뀔 수 있는 branch 이름만을 검증 근거로 쓰지 않는다. 조회한 SHA와 비교한다.
- 로컬 worktree 목록만으로 다른 컴퓨터·세션의 미사용을 증명하지 않는다. 공유 branch는 소유·협업 약속을 확인하고 이력이 불분명하면 자동 재작성하지 않는다.

## 3. base가 전진했을 때

| 관찰 | 대응 |
|---|---|
| B0 = 현재 base | head·검증 결과의 신선도 확인 후 다음 단계 |
| B0의 후손 B1, 직접 경로 비겹침 | rename 포함 diff와 생산자/소비자·공유 설정의 의미 영향 확인. B1+H0 통합 가능성과 필요한 검증 확인 후 근거 갱신 |
| 같은 경로·계약·의존성 변경 | 변경 의도를 대조하고 최신 base에 맞게 통합·수정한 뒤 영향을 받은 검증·리뷰 다시 수행 |
| B1이 B0의 후손이 아님 | 원격 이력 재작성/대상 변경 가능성. 이전 기준을 보존하고 원인을 확인하기 전 자동 rebase·force push·머지 금지 |
| branch 이름/PR base 자체 변경 | 새 대상의 정책·diff·검증 요구를 다시 확인. 기존 승인 범위를 바꾸는지 판단 |

`충돌 없음`, `변경 경로 비겹침`, `GitHub MERGEABLE`은 각각 의미적 호환성·테스트 통과·출고 승인을 증명하지 않는다. 예: base가 API 필드를 바꾸고 head가 다른 프런트 파일에서 이전 필드를 소비하면 Git merge는 성공해도 동작은 깨진다.

rebase 자체를 항상 의무로 삼지 않는다. 프로젝트가 허용하고 B1+H0 통합 결과를 검증할 수 있으면 branch를 유지할 수 있다. base 최신화가 필수인 정책이면 실제 업데이트와 fresh 검증을 수행한다.

통합이 필요하면 작업 소유·dirty·공유 여부와 프로젝트 merge/rebase 정책을 먼저 확인한다. 승인된 의미·범위 안의 통합·재검증은 반복 승인 없이 진행한다. 충돌 해소가 새로운 제품 결정이나 타 작업 변경을 요구하면 그 결정만 확인한다. abort·복구 시 사용자 작업이 없어지는 명령을 쓰지 않는다.

## 4. head 변경과 push

원격 head H1이 예상 H0와 다르면 먼저 새 커밋의 작성 주체·의도를 확인한다. 자신의 후속 커밋이어도 이전 검증을 새 HEAD에 자동 승계하지 않는다.

기본 push는 현재 작업 branch 한 개의 정상 fast-forward다. 거부되면 fetch·원인 확인 후 처리한다. 다른 작업의 원격 커밋을 덮어쓰거나 여러 branch를 연쇄 push하지 않는다.

rebase로 공개 이력을 바꾸는 경우 공유 branch·하위 PR 영향과 기존 허용 범위를 확인한다. 필요한 경우에만 **명시한 예상 원격 SHA**의 lease를 사용한다. 예: `--force-with-lease=refs/heads/<head>:<예상SHA>`. 예상값 없는 lease는 다른 세션의 fetch로 기준이 바뀔 수 있다. lease 실패를 통과시키려고 새 tip만 다시 읽고 강제 재시도하지 않는다. 변경된 작업을 검토·통합하는 단계로 돌아간다.

## 5. 재검증 범위와 머지 직전 경쟁

검증이 어느 (base SHA, head SHA, 설정/환경)에 대해 수행됐는지 남긴다. 이동하면 무효가 된 검증을 다시 수행한다. 예전 head의 초록 CI나 바뀌기 전 통합 결과를 현재 검증으로 취급하지 않는다. 필수 프로젝트 검증을 비용 이유로 생략하지 않는다.

머지 직전 원격 base/head, PR 대상, 필수 CI·리뷰와 unresolved blocker를 재조회한다. base가 또 움직이면 새 차이를 판단한다. 계속 전진해 기준을 확보하지 못하면 무한 재시도하지 말고 머지 큐·작업 조율 등으로 전환한다.

`gh pr merge --match-head-commit`은 head를 조건으로 걸며 **base를 고정하지 않는다**. fetch 직후 검증만으로 머지까지의 경쟁이 원자적으로 차단되었다고 주장하지 않는다.

- 서버의 최신 base 통합 검증·필수 체크·머지 큐가 있으면 해당 정책으로 최종 통합 결과를 확인한다. 큐 등록/auto-merge 예약은 MERGED가 아니므로 브랜치를 정리하지 않는다.
- 서버 보호가 없고 동시 머지 가능성이 있으면 자동 머지를 멈추고 현재 검증 기준과 경쟁 구간을 알린다. 이미 허용된 단일 머지 조율 방식이 있으면 그것을 따른다. 저장소 보호 설정을 임의 변경하지 않는다.
- 단독 작업에서 수행하는 최종 조회도 경쟁 가능성을 완전히 제거하지 않는다. 실제 merge 결과와 검증 기준을 대조해 예상과 다른 base 변경이 끼었으면 머지 완료·사후 검증 필요 상태를 보고한다. 자동 revert로 다른 작업을 되돌리지 않는다.

## 6. 정리 단계도 동시에 변할 수 있다

MERGED·merge commit·실제 base 반영을 확인한 뒤, 삭제 직전 다시 head tip·하위 PR·worktree·작업 소유를 확인한다. 원격 tip이 달라졌으면 보존한다. 로컬 main/develop이 다른 worktree에서 사용 중이면 그 worktree를 강제 전환·수정하지 않는다. 원격 머지와 로컬 정리 상태를 분리한다.

브랜치 삭제 lease는 ref 전진을 막는 조건이지 새로운 하위 PR 생성까지 원자적으로 막는 장치는 아니다. 공유·의존 작업의 사용 여부가 불분명하면 보존하고 정리 대기 사유를 남긴다. 작업 완료 시 검토 B/H, 실제 merge SHA, 정리/보존 결과와 미검증 범위를 기존 worklog에 갱신한다.
